# 014 — Публичный HTTPS для Mini App

Статус: **работает, живьём в Telegram не проверено** (нет токена бота в `.env` — см. «Что осталось»). Сделано 2026-09-06.

Снимает блокер фазы 1: до сих пор всё, что сделано в `008`–`013`, проверялось только в браузере. Telegram открывает Mini App **на телефоне покупателя**, поэтому адрес приложения должен резолвиться из интернета и отвечать по HTTPS с валидным сертификатом. Локального `https://127.0.0.1` — хоть с самоподписанным сертификатом, хоть с чужим — для этого недостаточно: до него из клиента просто нет маршрута.

Это ещё не деплой из роадмапа: адрес живёт, пока на машине разработчика работает туннель. Это способ проверить живьём то, что уже написано, не заводя облако.

## Что сделано

### Один origin вместо двух

`VITE_API_URL` стал относительным `/api`, а фронт и API съехались за один адрес: nginx в контейнере `telegram-app` проксирует `/api/*` на NestJS, Vite в дев-режиме — тем же путём на `127.0.0.1:3001`.

Причина не в удобстве. Приложение под туннелем отдаётся по HTTPS, а API до сих пор жил на `http://127.0.0.1:3001` — такой запрос браузер Telegram зарежет как mixed content, и это было бы не «каталог не грузится», а пустой экран без внятной ошибки. Отдельный HTTPS-адрес для API решал бы mixed content, но требовал второго туннеля, второго набора адресов в `.env` и CORS-вайтлиста, который надо переписывать при каждом новом адресе. Один origin убирает всё это разом: туннель ровно один, CORS не участвует, `.env` не зависит от того, какой адрес выдал туннель сегодня.

Дев и прод при этом ходят одним и тем же путём, а не расходятся ровно в том месте, которое ломается только в клиенте.

Две детали, которые обязательны и неочевидны:

- **`resolver 127.0.0.11` и адрес апстрима в переменной.** Без переменной nginx резолвит `api` один раз при старте и падает с `host not found in upstream`, если API ещё не поднялся: `depends_on` в compose ждёт запуска контейнера, а не готовности приложения.
- **`rewrite ^/api/(.*)$ /$1 break`.** С переменной в `proxy_pass` nginx перестаёт срезать префикс локейшена сам, а у NestJS глобального префикса нет — ручки лежат в корне (`/catalog`, `/auth`, `/orders`).

### Туннель как сервис compose

```bash
docker compose --profile tunnel up -d          # поднимет и туннель
docker compose logs tunnel | grep trycloudflare  # адрес для BotFather
```

Профиль, а не обычный сервис: обычная разработка идёт по `127.0.0.1:8080` и наружу светиться не должна. Образ `cloudflare/cloudflared` вместо установки в систему — чтобы у второй машины (и второй сессии) шаг был тот же самый.

### `allowedHosts` у Vite

Дев-сервер отвергает незнакомый `Host` («Blocked request. This host is not allowed») — это защита от DNS rebinding, а не помеха. В список добавлены домены туннелей: если понадобится выставить наружу именно дев-сборку с HMR, это перестанет упираться в белый список.

## Почему не ngrok

Выбирали его — ради бесплатного статического домена: адрес в BotFather вставляется один раз и не протухает при перезапуске, в отличие от случайного `*.trycloudflare.com`.

Проверка живым запросом это отменила. На бесплатном тарифе ngrok отвечает браузерам не приложением, а страницей-предупреждением:

```
Ngrok-Error-Code: ERR_NGROK_6024   →  "You are about to visit ..."
```

Проходит только запрос с заголовком `ngrok-skip-browser-warning`, а вебвью Telegram его не отправляет и добавить его некуда: страницу грузит клиент, а не наш код. Покупатель увидел бы заглушку ngrok вместо магазина. У `trycloudflare` такой страницы нет — проверено тем же запросом с мобильным User-Agent, отдаётся сразу `index.html`.

Статический адрес остаётся полезным, но он платный (ngrok) или требует своего домена в Cloudflare (именованный туннель). До первого настоящего деплоя это лишние деньги за то, что закрывается одной вставкой адреса в BotFather.

### Что туннель меняет в требованиях к `.env`

Пока API слушал только `127.0.0.1`, дефолты из `.env.example` были безобидны. Туннель выставляет наружу весь стек вместе с `/api/*`, и два поля перестают быть формальностью:

- **`JWT_SECRET`** — `change-me` за публичным адресом означает, что токен покупателя подделает кто угодно. Нужна длинная случайная строка.
- **`VITE_API_URL=/api`** — у клонов, заведённых до этой фичи, в `.env` лежит `http://127.0.0.1:3001`, а `.env` в `.gitignore`, и обновлённый `.env.example` их не догонит. Со старым значением бандл соберётся с абсолютным http-адресом и даст ровно тот mixed content, ради которого всё это делалось.

Найдено ревью — и то, и другое выглядело в диффе нормально, потому что менялось не в этих файлах.

### Три находки поменьше, оттуда же

- **`absolute_redirect off`** в nginx. Свои редиректы он собирает по `$scheme`, а до контейнера запрос доходит по http: `GET /api` отвечал `Location: http://<хост>/api/` и уводил клиента с HTTPS. Проверено запросом с подставленным `Host`.
- **Порт API в дев-прокси** больше не захардкожен: читается из корневого `.env` через `loadEnv`, потому что `PORT` там и задаётся (в `002` описан конфликт портов, из-за которого он не 3000). Разошлись бы молча — 502 вместо каталога на чужой машине.
- **`allowedHosts` не делает дев-сборку доступной снаружи сам по себе**: нужен ещё `--host 0.0.0.0` и свой `server.hmr`, иначе HMR стучится в `wss://<хост-туннеля>:5173`. Комментарий в конфиге это теперь говорит прямо, чтобы список не читался как обещание.

## Проверено

Живой стек в Docker (postgres+redis+api+nginx), миграции применены, каталог засеян (4 категории, 28 товаров). Запросами снаружи, с мобильным User-Agent, через настоящий HTTPS-адрес туннеля:

- `GET /` — 200, отдаётся `index.html` приложения (`<title>Микки Шоп</title>`), JS 286 КБ и CSS 14 КБ — 200.
- `GET /api/health` — `{"status":"ok"}`; `GET /api/catalog/products`, `/api/catalog/categories` — данные из живой БД.
- `GET /profile` — 200 (SPA-фоллбэк на `index.html` не сломан прокси-локейшеном).
- `POST /api/auth/telegram` — 401 «Вход через Telegram не настроен»: без `TELEGRAM_BOT_TOKEN` вход выключен целиком, как и задумано в `008`.
- Тот же набор по `http://127.0.0.1:8080` — чтобы отделить поломку прокси от поломки туннеля.

## Что осталось

- **`TELEGRAM_BOT_TOKEN` в `.env`** — без него вход выключен, а значит недоступны корзина с заказом от лица покупателя, профиль и питомцы. Ключи в `.env` заведены пустыми.
- **`MANAGER_CHAT_ID`** — пока пуст, заявки о заказах уходят в лог сервера (см. `009`).
- **Настоящий деплой** — пункт фазы 1 остаётся открытым: туннель живёт, пока работает машина разработчика.
- **Стабильный адрес** — при каждом перезапуске туннеля адрес меняется и его надо заново вставить в BotFather.
