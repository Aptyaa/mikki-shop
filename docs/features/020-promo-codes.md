# 020 — Промокоды

Статус: **план** — код не написан. Ступень G3 трека `docs/roadmap-game.md`.

**Это фича магазина, а не игры.** Промокоды нужны сами по себе: акция под
запуск, компенсация за задержку заказа, возврат ушедшего покупателя. Игра станет
одним из поводов выдать код, но не единственным и не первым. Поэтому ступень
можно делать в любой момент — кода игры она не требует, и в основном роадмапе ей
место в фазе 2.

## Решения, зафиксированные заранее

- **Фиксированная сумма, не процент.** Магазин ещё ничего не продал. Скидывать
  проценты с непроверенной цены — значит проверять спрос на искажённой цене.
- **С порогом корзины.** Иначе код целиком уносит маржу на дешёвом аксессуаре.
- **С коротким сроком жизни** (по умолчанию 48 часов). Срок и есть то, что
  превращает код в повод вернуться; бессрочный код лежит мёртвым грузом.
- **Один активный код на человека.** Не копятся, не складываются, на один заказ
  — один код.
- **Номинал, порог и срок — настройки, а не константы в исходнике.** Их будет
  крутить владелец, а не разработчик.

## Данные

```prisma
/// Правило скидки: «500 ₽ при корзине от 3000 ₽». Шаблон, из которого
/// выпускаются коды конкретным людям.
model Promo {
  id          String   @id @default(uuid())
  key         String   @unique   // "game-streak-5"
  title       String             // видит покупатель: «За серию в игре»
  /// Целые рубли, как и Product.price. Процентов нет намеренно — см. выше.
  amount      Int
  /// Минимальная сумма корзины, при которой код применяется.
  minTotal    Int
  /// Сколько живёт выпущенный код.
  ttlHours    Int      @default(48)
  active      Boolean  @default(true)
  createdAt   DateTime @default(now())

  grants      PromoGrant[]
}

/// Выпущенный код: конкретный человек, конкретный срок.
model PromoGrant {
  id        String   @id @default(uuid())
  promoId   String
  promo     Promo    @relation(fields: [promoId], references: [id])
  userId    String
  user      User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  /// Код, который видит покупатель. Уникален глобально.
  code      String   @unique
  expiresAt DateTime
  usedAt    DateTime?
  /// Заказ, в котором код сработал. Пусто, пока не использован.
  orderId   String?  @unique

  createdAt DateTime @default(now())

  @@index([userId])
}
```

`Order` получает два поля: `discount Int @default(0)` и `promoCode String?` —
**слепком, а не ссылкой**, ровно по той же причине, по которой кличка питомца в
заказе стала слепком в `011`: заказ должен читаться через год, даже если правило
скидки давно удалено.

### Почему код хранится открытым, а не хэшем

В `AdminInvite` код хранится хэшем — там утечка означает чужого менеджера в
магазине. Здесь цена утечки — 500 ₽ и один заказ, а покупателю нужно видеть свой
код в кабинете и переслать его. Хэш сделал бы это невозможным ради защиты от
угрозы, которой нет.

Но код должен быть **неугадываемым**: генерируется из криптографического
случайного источника, а не из даты или счётчика. Иначе перебор соседних кодов
раздаёт скидки всем желающим.

## API и где считается скидка

Скидка считается **только на бэкенде**, в тех же местах, где уже считается цена:

- `POST /cart/preview` принимает необязательный код. Ответ дополняется суммой
  скидки, итогом и — если код не подошёл — причиной («до 3000 ₽ не хватает
  400 ₽», «срок истёк»). Причина обязательна: «код не применился» без объяснения
  — это претензия в чат менеджеру.
- `POST /orders` принимает код, перепроверяет всё заново и помечает
  `PromoGrant.usedAt`/`orderId` **в той же транзакции**, что и списание остатков.
  Иначе два одновременных заказа применят один код дважды.
- `GET /promo/my` — активные коды покупателя для экрана профиля.

Клиент скидку не считает никогда. Как и с ценами в `007`, единственный источник
правды — сервер.

## Что видит покупатель и менеджер

- **Профиль**: строка «Ваш промокод» с кодом, номиналом, порогом и сроком.
  Истёкшие не показываются.
- **Корзина**: поле для кода, под итогом — строка скидки.
- **Заявка менеджеру** в боте: строка «Скидка по коду X: −500 ₽». Без неё
  менеджер увидит сумму меньше ожидаемой и решит, что это ошибка.

## Что здесь легко сделать неправильно

- **Скидка ниже нуля.** Итог не может стать отрицательным: скидка ограничена
  суммой корзины. Проверяется тестом, а не надеждой на порог.
- **Двойное применение.** Два заказа в одну секунду — реальный сценарий при
  двойном тапе. Спасает только транзакция и `@unique` на `orderId`.
- **Отмена заказа.** Остатки при отмене возвращаются (`016`), а код —
  **не возвращается**. Иначе отмена превращается в способ пользоваться кодом
  бесконечно. Это решение, а не недосмотр, и его стоит проговорить владельцу.
- **Порог и остатки.** Корзина пересчитывается перед оформлением (`007`), и
  сумма может упасть ниже порога, если позиция разобрана. Тогда код отваливается
  — с объяснением, а не молча.

## Готово, когда

- Код применяется в корзине и попадает в заказ, скидка видна менеджеру.
- Повторное применение невозможно — есть тест на два одновременных заказа.
- Истёкший, чужой, несуществующий и не дотягивающий до порога код дают внятную
  причину отказа.
