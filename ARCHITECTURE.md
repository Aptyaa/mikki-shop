# Архитектура

## Продукт
Интернет-магазин одежды для маленьких собак, интегрированный как Telegram Mini App (первая платформа) и VK Mini App (вторая платформа). Трафик приходит из Reels (Instagram) и TikTok и конвертируется в продажи внутри Telegram.

Продукт рассматривается как первая фаза более крупной платформы для владельцев собак: в перспективе — социальная сеть (поиск компаньонов для прогулок, вязки и т.д.). Архитектура закладывается так, чтобы это расширение не требовало переписывания ядра.

## Принцип: модульный монолит

Один деплоюмый бэкенд-сервис с чёткими доменными границами внутри. Не микросервисы — при нулевой/малой нагрузке это overengineering, замедлит MVP. Границы позволяют при росте нагрузки вынести любой модуль в отдельный сервис без переписывания бизнес-логики.

Модули:

- **Identity/User** — пользователь, привязка к TG id / VK id. Не зависит от коммерции.
- **Pet-профиль** — отдельная сущность с первого дня (порода, размер, кличка), даже если пока используется только как «получатель заказа» в магазине. Добавлять её позже, когда на Pet уже завязана социалка и поиск — дорого; сделать сразу — дёшево.
- **Commerce/Catalog** — товары, заказы, оплата. Ссылается на Pet, но не встроен в него напрямую.
- **Social/Matching** (зарезервировано, не строится в MVP) — посты, лента, геопоиск компаньонов/вязки. Подключается позже как подписчик событий, не трогая код магазина.

Связь между модулями — через событийную шину (на старте достаточно Redis Streams/pub-sub, без Kafka): `order.created`, `pet.created`, `user.registered` и т.д. Это даёт возможность подключать новые модули (уведомления, лента) как подписчиков событий.

## Стек

Решение зафиксировано: TypeScript на фронте и бэке — общие типы между всеми приложениями без дублирования контрактов, что критично для соло-разработки с AI-агентом.

**Монорепо** (pnpm workspaces):
```
apps/
  telegram-app/   — React + Vite, TG адаптер
  vk-app/         — React + Vite, VK адаптер (фаза 5)
  admin/          — React + Vite, самописная админка
  api/            — NestJS
packages/
  shared-types/   — DTO/типы, общие для всех apps
  ui/             — общие UI-компоненты каталога/корзины
```

- **Frontend**: React + Vite + TypeScript. Общая бизнес-логика и компоненты, платформенные SDK изолированы в адаптерах:
  - Telegram: `@telegram-apps/sdk` (или `@twa-dev/sdk`)
  - VK: `@vkontakte/vk-bridge` + VKUI (только для навигационного «шасси» VK-приложения — таббар/шапка; карточки товаров и каталог остаются общими кастомными компонентами ради бренд-консистентности)
- **Стилизация**: Tailwind CSS, значения — CSS-переменные из общего пакета design tokens (`packages/ui`), а не хардкод. Tailwind config ссылается на переменные. Тема (свет/тёмная) берётся из `themeParams` Telegram и `scheme` VK Bridge при старте, не изобретаем свой переключатель. Варианты компонентов — `class-variance-authority`.
- **Backend**: NestJS + TypeScript, **Prisma** как ORM (schema-first, автогенерация типов в монорепо).
- **Auth**: единый JWT, выпускается бэкендом после проверки подписи `initData` от Telegram (позже — launch-параметров VK).
- **БД**: PostgreSQL + расширение **PostGIS** включено с самого начала (нужно для будущего геопоиска «прогулки/вязки рядом» — добавить расширение сейчас бесплатно, мигрировать на него позже больно). Managed Postgres в российском облаке (Yandex Cloud / Selectel) — данные пользователей РФ хранятся в РФ (152-ФЗ).
- **Кеш/очереди**: managed Redis в том же облаке (сессии, корзина, событийная шина).
- **Хранилище файлов**: Yandex Object Storage (S3-совместимое) — фото товаров, позже фото питомцев/постов.
- **Оплата**: Telegram Payments API с ЮKassa как провайдером, позже VK Pay.
- **Admin**: отдельное SPA в монорепо (`apps/admin`), тот же NestJS API с ролевым guard — не отдельная система.
- **Инфраструктура**: Docker → GitHub Actions → Yandex Container Registry → деплой в том же облаке.

## Аналитика воронки трафика

Deep-link с UTM в `start`-параметре Telegram-бота (`t.me/bot?start=utm_source_tiktok_campaign1`). Источник логируется на первом же событии пользователя и прокидывается через всю воронку до оплаты — без этого невозможно понять, какой контент в Reels/TikTok конвертит в продажи.

## Почему это масштабируется

- Identity и Pet-профиль как отдельные от Commerce сущности с первого дня — социальные фичи позже используют те же профили, не требуя миграции данных.
- PostGIS включён заранее — геопоиск компаньонов добавляется без смены БД.
- Событийная шина — новые модули (лента, мэтчинг, уведомления) подключаются как подписчики, не трогая код магазина.
- Модули внутри монолита физически разделены (папки/пакеты) так, что при реальной нагрузке любой модуль можно вынести в отдельный сервис.
